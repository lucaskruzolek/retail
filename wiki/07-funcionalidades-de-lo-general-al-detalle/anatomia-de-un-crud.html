Fundamentos

Anatomía de un CRUD

El esqueleto que repite casi todo módulo de Retail: quién es cada pieza, cómo se ve en código, cómo se conectan con la inyección de dependencias y cómo el Unit of Work hace que se guarde todo o nada. El ejemplo es el alta, la edición, la baja y el listado de clientes. Contrastado con el código el 11 de noviembre de 2026.

Este documento no cuenta una funcionalidad: cuenta la forma que tienen todas. Si entendés cómo viaja un dato desde que el usuario aprieta «Guardar» en la pantalla de clientes hasta que queda en SQL Server, entendés el 80 % de cualquier otro módulo (artículos, proveedores, usuarios, pedidos). Lo que cambia de uno a otro son las reglas de negocio, no el camino.

El ejemplo es Cliente (RF-20) porque tiene todas las piezas y reglas reales (documento válido, nombre de persona o razón social, baja lógica con restricciones). El servicio de clientes también registra cobranzas de cuenta corriente: ese tramo se deja afuera a propósito, porque agrega a la caja y al ticket y distraería del esqueleto. Los fragmentos de código son reales y recortados (los ... marcan lo omitido) y cada uno dice de qué archivo sale.

1 · El mapa

Abstracción máxima

Retail está dividido en cuatro proyectos con una regla que el compilador hace cumplir: las dependencias solo apuntan hacia adentro. El dominio no conoce a nadie; la aplicación conoce al dominio; la infraestructura y la pantalla conocen a la aplicación, pero nunca entre sí.

La flecha punteada es la única excepción, y es de arranque: App.xaml.cs necesita conocer a Infraestructura para registrar sus clases en el contenedor. Una pantalla jamás usa el DbContext: toda operación pasa por un servicio de Aplicación (Ley 1).

El recorrido de un «Guardar»

Así viaja un alta de cliente, desde que el formulario avisa al ViewModel hasta el INSERT. Cada participante es una de las piezas que vas a ver con su código en la sección 2; el formulario, el validador y la entidad aparecen como pasos para que el diagrama entre en pantalla.

Además hay dos piezas que no son de «clientes» pero hacen que todo funcione y tienen su propia sección: el contenedor de inyección de dependencias (sección 4) y el Unit of Work (sección 5).

Qué tenés que llevarte
  • Cada pieza hace una sola cosa y vive en una carpeta predecible. Si no sabés dónde va algo, la tabla de arriba responde.
  • El dominio decide qué es válido; el servicio decide en qué orden pasan las cosas; la infraestructura decide cómo se guarda; la pantalla decide cómo se ve.
  • Todo se entrega por interfaces definidas en Aplicación. Por eso se puede cambiar o reemplazar una pieza (por ejemplo, en una prueba) sin tocar las demás.

2 · Los actores uno por uno

Cada pieza con su código real

1 · La base: BaseEntity y IAggregateRoot

Toda entidad hereda de BaseEntity. De ahí salen el id, la fecha de creación y, sobre todo, la baja lógica: en un sistema comercial nunca se borra una fila, se la marca como dada de baja (Ley 3).

src/Retail.Domain/Common/BaseEntity.cs

public abstract class BaseEntity
{
    public int Id { get; set; }
    public DateTime CreatedAt { get; set; } = DateTime.UtcNow;
    public DateTime? DeletedAt { get; set; }
    public bool IsDeleted => DeletedAt.HasValue;

    public virtual void MarkAsDeleted()
    {
        DeletedAt = DateTime.UtcNow;
    }

    public void Restore()
    {
        DeletedAt = null;
    }
}

IAggregateRoot es una interfaz vacía que funciona como etiqueta: «esta entidad es la puerta de entrada de su grupo». Solo las raíces tienen repositorio (Ley 2). Por ejemplo, Cliente es raíz y sus Cobranzas se manipulan a través de Cliente.RegistrarCobranza(...); no existe un «repositorio de cobranzas».

  • Qué NO hace: no sabe nada de bases de datos. El borrado lógico es solo una fecha; quien la filtra es la infraestructura (ver pieza 9).

2 · La entidad: Cliente

Es una raíz de agregado: el único lugar donde viven las reglas de negocio de un cliente. Tiene tres rasgos que se repiten en todas las entidades:

  • Propiedades con private set. Nadie desde afuera puede asignar un nombre inválido: solo se cambia a través de métodos que validan.
  • Un constructor privado que solo usa EF Core para reconstruir la entidad desde la base. El código de negocio usa el método fábrica Crear.
  • Métodos con nombre de negocio (ActualizarDatos, HabilitarCuentaCorriente) en lugar de setters sueltos.

src/Retail.Domain/Entities/Cliente.cs (recortado)

public class Cliente : BaseEntity, IAggregateRoot
{
    // Lo usa EF Core para materializar la entidad; el código de negocio usa Crear.
    private Cliente()
    {
    }

    public string RazonSocialONombre { get; private set; } = string.Empty;
    public TipoDocumentoEnum TipoDocumento { get; private set; } = TipoDocumentoEnum.Dni;
    public string NumeroDocumento { get; private set; } = string.Empty;
    // ... condición de IVA, domicilio, teléfono, email, cuenta corriente ...

    public static Cliente Crear(
        string razonSocialONombre,
        TipoDocumentoEnum tipoDocumento,
        string numeroDocumento,
        CondicionIvaEnum condicionIva,
        string? domicilioFiscal = null,
        string? telefono = null,
        string? email = null)
    {
        var cliente = new Cliente();
        cliente.ActualizarDatos(razonSocialONombre, tipoDocumento, numeroDocumento,
            condicionIva, domicilioFiscal, telefono, email);
        return cliente;
    }

    public void ActualizarDatos(/* los mismos parámetros */)
    {
        if (!Enum.IsDefined(tipoDocumento))
        {
            throw new DomainException($"El tipo de documento '{tipoDocumento}' no es válido.");
        }

        // Se validan todos los valores antes de asignar alguno:
        // el agregado nunca queda a medio actualizar.
        var documentoNormalizado = ReglasDocumento.Exigir(tipoDocumento, numeroDocumento);
        // ... el resto de las reglas ...

        NumeroDocumento = documentoNormalizado;
        // ... se asignan todos juntos ...
    }

    public override void MarkAsDeleted()
    {
        if (SaldoCuentaCorriente > 0m)
        {
            throw new InvalidOperationException("No se puede dar de baja al cliente porque mantiene un saldo deudor ...");
        }

        base.MarkAsDeleted();
    }
}
  • Dos detalles para fijarse. Crear reutiliza ActualizarDatos: la regla se escribe una sola vez. Y ActualizarDatos valida todo antes de asignar nada, así un error en el tercer campo no deja el cliente con el primero ya cambiado. La baja (MarkAsDeleted) también tiene regla: no se da de baja a quien debe plata.
  • Qué NO hace: no consulta la base, no llama a otros servicios, no sabe que existe una pantalla. Es código puro de C#: se prueba sin base de datos (Retail.Domain.UnitTests).

3 · Los DTO

Un DTO (Data Transfer Object) es un objeto «tonto»: solo transporta datos entre capas. Hay uno por cada dirección y propósito: uno para pedir un alta, otro para pedir una edición, otro para devolver un cliente a la pantalla. Se escriben como record de C#, que son inmutables y comparan por valor.

src/Retail.Application/DTOs/Clientes/CrearClienteDto.cs

public record class CrearClienteDto
{
    public required string RazonSocialONombre { get; init; }
    public required TipoDocumentoEnum TipoDocumento { get; init; }
    public required string NumeroDocumento { get; init; }
    public required CondicionIvaEnum CondicionIva { get; init; }
    public string? DomicilioFiscal { get; init; }
    public string? Telefono { get; init; }
    public string? Email { get; init; }
    public bool TieneCuentaCorriente { get; init; }
    public decimal LimiteCredito { get; init; }
}

El DTO de salida, ClienteDto, hereda de BaseDto y trae algunos campos calculados que la pantalla muestra (CreditoDisponible, TieneDeuda). required obliga al compilador a exigir los datos obligatorios al construirlo.

  • Por qué no usar la entidad directamente en la pantalla: la entidad tiene reglas y relaciones (Ventas, Cobranzas) que la pantalla no debe tocar, y exponerla permitiría saltear sus validaciones. El DTO es el contrato mínimo.
  • Qué NO hace: no valida ni calcula reglas de negocio.

4 · El validador

El validador revisa la entrada en la frontera, con la librería FluentValidation, y devuelve todos los errores juntos (no el primero). Se escribe de forma declarativa: «esta propiedad tiene que cumplir esta regla».

src/Retail.Application/Validators/Clientes/CrearClienteValidator.cs (recortado)

public class CrearClienteValidator : AbstractValidator<CrearClienteDto>
{
    public CrearClienteValidator()
    {
        RuleLevelCascadeMode = CascadeMode.Stop;

        RuleFor(x => x.TipoDocumento)
            .IsInEnum().WithMessage("Debe especificar un tipo de documento válido.");

        RuleFor(x => x.RazonSocialONombre)
            .NombreDeCliente(x => x.TipoDocumento);

        RuleFor(x => x.NumeroDocumento)
            .DocumentoSegunTipo(x => x.TipoDocumento);

        RuleFor(x => x.LimiteCredito)
            .GreaterThanOrEqualTo(0m).WithMessage("El límite de crédito no puede ser negativo.");
        // ... domicilio, teléfono y email opcionales ...
    }
}
  • Validador y dominio no se repiten: se complementan. El validador da mensajes por campo y los junta todos para que el usuario corrija de una vez. El dominio es la última barrera: garantiza que ninguna entidad inválida exista aunque alguien llame al método sin pasar por el validador. Para no duplicar reglas, el validador reutiliza las del dominio (por ejemplo, Cliente.EsNombreValido).
  • Qué NO hace: no consulta la base (verificar que el documento no esté repetido lo hace el servicio) ni modifica nada.

5 · El contrato del servicio

Una interfaz que lista, en lenguaje del negocio, lo que se le puede pedir al módulo. La pantalla depende de esta interfaz, no de la clase que la implementa.

public interface IClienteService
{

    Task ActualizarClienteAsync(ActualizarClienteDto dto, CancellationToken cancellationToken = default);
    Task BajaClienteAsync(int idCliente, CancellationToken cancellationToken = default);
    // ... búsqueda rápida y cobranzas ...

Fijate en los nombres: Crear, Actualizar, Baja, Listar, Obtener. Es el CRUD con el vocabulario del negocio: no hay «Delete», hay Baja, porque nunca se borra. Todos son async y reciben un CancellationToken, para que la pantalla pueda cancelar una consulta lenta (Ley 4).

6 · El servicio

El servicio de aplicación implementa un caso de uso. No contiene reglas de negocio (esas viven en la entidad): contiene el orden de los pasos. Sus dependencias llegan por el constructor.

src/Retail.Application/Services/ClienteService.cs (recortado)

public class ClienteService : IClienteService
{
    private readonly IRepository<Cliente> _clienteRepository;
    private readonly IUnitOfWork _unitOfWork;
    private readonly IValidator<CrearClienteDto> _crearClienteValidator;
    // ... otros validadores, caja y ticket (para cobranzas) ...
    private readonly IClienteQueryService? _clienteQueryService;

    public ClienteService(
        IRepository<Cliente> clienteRepository,
        IUnitOfWork unitOfWork,
        IValidator<CrearClienteDto> crearClienteValidator,
        /* ... */
        IClienteQueryService? clienteQueryService = null)
    {
        _clienteRepository = clienteRepository ?? throw new ArgumentNullException(nameof(clienteRepository));
        _unitOfWork = unitOfWork ?? throw new ArgumentNullException(nameof(unitOfWork));
        // ...
    }

    public async Task<ClienteDto> CrearClienteAsync(CrearClienteDto dto, CancellationToken cancellationToken = default)
    {
        ArgumentNullException.ThrowIfNull(dto);
        await _crearClienteValidator.ValidateAndThrowAsync(dto, cancellationToken);

        // Se compara la forma canónica: "12.345.678" y "12345678" son el mismo DNI.
        string documentoNormalizado = ReglasDocumento.Normalizar(dto.TipoDocumento, dto.NumeroDocumento);

        var existente = await _clienteRepository.FindAsync(c => c.NumeroDocumento == documentoNormalizado, cancellationToken);
        if (existente.Count > 0)
        {
            throw new InvalidOperationException($"Ya existe un cliente activo con el número de documento '{documentoNormalizado}'.");
        }

        var cliente = Cliente.Crear(dto.RazonSocialONombre, dto.TipoDocumento, dto.NumeroDocumento,
            dto.CondicionIva, dto.DomicilioFiscal, dto.Telefono, dto.Email);

        if (dto.TieneCuentaCorriente)
        {
            cliente.HabilitarCuentaCorriente(dto.LimiteCredito);
        }

        await _clienteRepository.AddAsync(cliente, cancellationToken);
        await _unitOfWork.SaveChangesAsync(cancellationToken);

        return MapToDto(cliente);
    }
}

Leé CrearClienteAsync como una receta de seis pasos, que es el patrón de cualquier alta:

PasoLíneaQuién resuelve el problema
1ValidateAndThrowAsyncEl validador: ¿la entrada tiene forma correcta?
2FindAsync(... NumeroDocumento ...)El repositorio: ¿ya existe? (regla que necesita la base, por eso vive en el servicio)
3Cliente.Crear(...)El dominio: construye una entidad válida o falla
4HabilitarCuentaCorrienteEl dominio: custodia su propia invariante
5AddAsyncEl repositorio: «anotá este cliente para guardarlo»
6SaveChangesAsyncEl Unit of Work: «guardá todo lo anotado, en una transacción»
  • Qué NO hace: no escribe SQL, no sabe de WPF, y no decide si un nombre es válido (le pregunta al dominio).

7 · El repositorio

El repositorio es una colección en memoria de raíces de agregado: se le pide una entidad, se le agrega una. Es genérico: un único Repository<T> sirve para todas las raíces, y la restricción where T : BaseEntity, IAggregateRoot hace cumplir la Ley 2 en tiempo de compilación.

src/Retail.Application/Interfaces/Persistence/IRepository.cs (recortado) y la implementación en src/Retail.Infrastructure/Persistence/Repositories/Repository.cs

public interface IRepository<T> where T : BaseEntity, IAggregateRoot
{
    Task<T?> GetByIdAsync(int id, CancellationToken cancellationToken = default);
    Task<IReadOnlyList<T>> FindAsync(Expression<Func<T, bool>> predicate, CancellationToken cancellationToken = default);
    Task<T> AddAsync(T entity, CancellationToken cancellationToken = default);
    Task UpdateAsync(T entity, CancellationToken cancellationToken = default);
    Task DeleteAsync(T entity, CancellationToken cancellationToken = default);
    // ... variantes con includeDeleted y con Include ...
}

// Implementación (Infraestructura)
public class Repository<T> : IRepository<T> where T : BaseEntity, IAggregateRoot
{
    private readonly RetailDbContext _context;
    private readonly DbSet<T> _dbSet;

    public Repository(RetailDbContext context)
    {
        _context = context ?? throw new ArgumentNullException(nameof(context));
        _dbSet = _context.Set<T>();
    }

    public virtual async Task<T> AddAsync(T entity, CancellationToken cancellationToken = default)
    {
        ArgumentNullException.ThrowIfNull(entity);
        await _dbSet.AddAsync(entity, cancellationToken);   // solo lo anota: NO guarda
        return entity;
    }

    public virtual Task DeleteAsync(T entity, CancellationToken cancellationToken = default)
    {
        ArgumentNullException.ThrowIfNull(entity);
        entity.MarkAsDeleted();                            // baja lógica, nunca DELETE
        _dbSet.Update(entity);
        return Task.CompletedTask;
    }
}
La idea que más cuesta ver. AddAsync no guarda nada. Solo le avisa al DbContext «seguí a esta entidad: está nueva». Guardar es trabajo del Unit of Work (sección 5). Por eso un servicio puede llamar a varios repositorios y guardar todo junto al final.
  • Qué NO hace: no hay un repositorio por entidad interna (DetalleVenta no tiene) ni consultas de listado con filtros y paginación (eso es la pieza 8).

8 · El servicio de consulta (el lado lectura)

Los listados con filtros, ordenamiento y paginación no pasan por el repositorio: tienen su propio servicio. La razón es la Ley 8: las búsquedas se resuelven dentro de SQL Server, sin traer miles de entidades a memoria, y proyectando directamente a DTO sin seguimiento de cambios (AsNoTracking). Es una versión liviana de CQRS: una vía para escribir (repositorio y entidad) y otra para leer (consulta y DTO).

src/Retail.Infrastructure/Persistence/Services/ClienteQueryService.cs (recortado)

public async Task<ClientesPaginadosDto> ObtenerClientesPaginadosAsync(
    ConsultaClientesDto consulta, CancellationToken cancellationToken = default)
{
    // Agregaciones nativas en el servidor

    IQueryable<Cliente> query = _context.Clientes.AsNoTracking();

    if (!string.IsNullOrWhiteSpace(consulta.TerminoBusqueda))
    {
        var term = consulta.TerminoBusqueda.Trim();
        query = query.Where(c =>
            EF.Functions.Like(c.RazonSocialONombre, $"%{term}%") ||
            EF.Functions.Like(c.NumeroDocumento, $"%{term}%"));

    // ... filtros por condición de IVA, deuda y cuenta corriente ...

        .OrderBy(c => c.RazonSocialONombre)
        .Skip((pagina - 1) * tamanoPagina)
        .Take(tamanoPagina)
        .ToListAsync(cancellationToken);

    var items = entidades.Select(c => new ClienteDto { /* ... */ }).ToList();
    // ...
}

El filtro, el orden, el conteo y la página se componen sobre IQueryable y EF Core los traduce a una sola consulta SQL. Solo viaja a memoria la página que se va a mostrar (por ejemplo, 10 clientes), no la tabla entera.

  • Qué NO hace: no modifica datos y no devuelve entidades (devuelve DTO). Su contrato IClienteQueryService vive en Aplicación y la clase en Infraestructura: es el ejemplo de puerto y adaptador.

9 · La configuración de EF

Le dice a Entity Framework Core cómo se guarda la entidad: nombre de tabla, nombres de columna, largos, índices y restricciones. Es la única pieza que conoce el esquema. Cada entidad tiene su archivo XConfiguration, y ApplyConfigurationsFromAssembly los encuentra solos: no hay que registrarlos.

src/Retail.Infrastructure/Persistence/Configurations/ClienteConfiguration.cs (recortado)

public class ClienteConfiguration : IEntityTypeConfiguration<Cliente>
{
    public void Configure(EntityTypeBuilder<Cliente> builder)
    {
        builder.ToTable("CLIENTES", t =>
        {
            t.HasCheckConstraint("CK_CLIENTES_LimiteCredito", "[limite_credito] >= 0");
            t.HasCheckConstraint("CK_CLIENTES_SaldoCuentaCorriente", "[saldo_cuenta_corriente] >= 0");
        });

        builder.Property(c => c.NumeroDocumento)
            .HasColumnName("numero_documento")
            .HasMaxLength(20)
            .IsRequired();

        // Único entre los clientes vigentes: un dado de baja libera su documento
        builder.HasIndex(c => c.NumeroDocumento)
            .IsUnique()
            .HasFilter("[deleted_at] IS NULL");

        builder.Property(c => c.TipoDocumento)
            .HasColumnName("tipo_documento")
            .HasConversion<string>()      // se guarda como texto legible
            .HasMaxLength(20);
        // ... el resto de las columnas ...
    }
}

Dos ideas para llevarte. Primera: las reglas importantes están dos veces, una en el dominio y otra en la base (CHECK de saldo y límite, índice único). El dominio da un mensaje claro; la base es la última barrera si algo se escapa o si dos terminales actúan a la vez. Segunda: el filtro deleted_at IS NULL del índice permite dar de baja a un cliente y después volver a registrar el mismo documento.

El filtro global de baja lógica no está en este archivo: está una sola vez en RetailDbContext, que lo agrega a todas las entidades que heredan de BaseEntity:

src/Retail.Infrastructure/Persistence/Context/RetailDbContext.cs (recortado)

// Aplicar Global Query Filter para Soft Delete en todas las entidades derivadas de BaseEntity
foreach (var entityType in modelBuilder.Model.GetEntityTypes())
{
    if (typeof(BaseEntity).IsAssignableFrom(entityType.ClrType))
    {
        var parameter = Expression.Parameter(entityType.ClrType, "e");
        var property = Expression.Property(parameter, nameof(BaseEntity.DeletedAt));
        var condition = Expression.Equal(property, Expression.Constant(null, typeof(DateTime?)));
        modelBuilder.Entity(entityType.ClrType).HasQueryFilter(Expression.Lambda(condition, parameter));
    }
}

Por eso _context.Clientes nunca devuelve los dados de baja, sin que nadie escriba Where(c => c.DeletedAt == null).

10 · El ViewModel de la lista

El ViewModel (patrón MVVM) es el intermediario entre la vista y los servicios. Guarda el estado de la pantalla (la lista, la fila seleccionada, el texto de búsqueda, si está ocupado) y expone comandos (los botones). {
    var cliente = await _clienteRepository.GetByIdAsync(idCliente, cancellationToken)

Hay una red de seguridad más. Si alguien llamara a DeleteAsync sobre un repositorio, o si EF marcara una entidad como Deleted, el SaveChangesAsync de RetailDbContext la convierte en una baja lógica antes de guardar:

foreach (var entry in ChangeTracker.Entries<BaseEntity>())
{

    {
        entry.State = EntityState.Modified;   // en lugar de DELETE, un UPDATE
        entry.Entity.MarkAsDeleted();

Qué tenés que llevarte
  • Los cuatro verbos siguen un mismo ritmo: validar, cargar o construir, pedirle al dominio, guardar.
  • Para escribir se usa el repositorio y la entidad; para mostrar se usa la consulta y el DTO. Mezclarlos es el error más común (cargar entidades para pintar una grilla).

Recién en _unitOfWork.SaveChangesAsync. AddAsync solo anota la entidad en el seguimiento de cambios del DbContext con el estado Added. Todo lo anotado hasta ese momento (de uno o de varios repositorios) se envía a SQL Server junto, dentro de una transacción. Si algo falla, no se guarda nada.

4 · Inyección de dependencias

Cómo se arma el grafo y por qué importan los ciclos de vida

El problema que resuelve

Mirá lo que necesita ClienteService para existir: un repositorio, un Unit of Work, tres validadores, un servicio de caja, un servicio de ticket y un servicio de consulta. Cada uno de ellos necesita, a su vez, un DbContext compartido. Si cada clase creara sus propias dependencias con new, sería algo así (ejemplo ilustrativo: esto no existe en el repositorio):

// SIN inyección de dependencias (ilustrativo)
var contexto = new RetailDbContext(opciones);
var servicio = new ClienteService(
    new Repository<Cliente>(contexto),
    new UnitOfWork(contexto),
    new CrearClienteValidator(),
    new ActualizarClienteValidator(),
    new RegistrarCobranzaValidator(),
    new CajaService(/* ...y sus propias dependencias... */),
    new FileDebugTicketPrinterService(),
    new ClienteQueryService(contexto));

Esto tiene tres problemas serios: cada pantalla repetiría esta construcción; una distracción (olvidarse de pasar el mismo contexto a todos) rompe la transacción en silencio; y la clase queda atada a implementaciones concretas, así que para probarla habría que usar una base de datos real.

La inyección de dependencias invierte el control. Una clase declara qué necesita en su constructor (como interfaces) y alguien más, el contenedor, se ocupa de construir el grafo completo. Es el principio de inversión de dependencias de SOLID: las clases dependen de abstracciones, no de detalles.

El grafo de ClientesView

Cuando se navega a la pantalla de clientes, el contenedor resuelve la vista y construye hacia adentro todo lo que haga falta. Vos no escribís esto en ningún lado: sale de los constructores.

Los tres ciclos de vida

Cuando el contenedor entrega una instancia, hay que decidir cuánto vive. Son tres opciones, y elegir mal rompe cosas:

¿Y qué es un alcance? En Retail, un alcance por pantalla. NavigationService crea uno nuevo cada vez que se navega y descarta el anterior:

  • Dos pantallas nunca comparten DbContext ni, por lo tanto, entidades rastreadas. Lo que una modifique sin guardar no contamina a la otra. Hay una prueba que lo verifica (RegistrarServicios_DosScopes_ResuelvenDbContextDistintos).
  • Al salir de una pantalla se libera todo: el contexto y sus entidades (importa para el límite de memoria, RNF-03) y los ViewModels que implementan IDisposable, que cancelan sus cargas pendientes.
  • Los servicios de diálogo son Scoped a propósito: un modal usa el mismo DbContext que la pantalla que lo abre.

La trampa: un Singleton que depende de algo Scoped

Un Singleton vive toda la aplicación; un Scoped vive una pantalla. Si un Singleton recibiera un DbContext por constructor, ese contexto quedaría capturado para siempre (se lo llama captive dependency): viviría más que la pantalla, acumularía entidades y compartiría estado entre pantallas.

La solución del proyecto es doble. Primero, el Singleton que necesita servicios Scoped no los recibe: recibe una IServiceScopeFactory y crea un alcance cuando lo necesita (así lo hacen NavigationService y MainViewModel). Segundo, el arranque está configurado para fallar ruidosamente ante el error:

Autoevaluación 4: ¿por qué ClientesViewModel es Transient y no Singleton?

Porque guarda estado de una pantalla (la lista cargada, la fila seleccionada, el texto de búsqueda) y depende de servicios Scoped (IClienteService usa el DbContext de la pantalla). Si fuera Singleton, viviría más que su contexto (captive dependency) y mostraría datos de una visita anterior. Como Transient, se crea cuando se abre la pantalla dentro de su alcance y desaparece con él. Por la misma razón, las vistas también son Transient.

5 · Unit of Work

Repositorio frente a transacción

El problema: guardar varias cosas como una sola

Muchas operaciones modifican más de una entidad: una venta descuenta stock de varios artículos y registra pagos; una compra suma stock y cierra un pedido. Si el sistema se cae a mitad de camino, no puede quedar la compra registrada y el stock sin sumar. Hace falta una unidad de trabajo: un conjunto de cambios que se confirman todos o ninguno (la «A» de ACID, atomicidad).

Repositorio y Unit of Work no son lo mismo

src/Retail.Application/Interfaces/Persistence/IUnitOfWork.cs (recortado)

public interface IUnitOfWork : IDisposable
{
    /// Confirma los cambios pendientes en una única transacción.
    /// Lanza ConflictoDeConcurrenciaException si otro usuario modificó los mismos datos.
    /// Lanza RestriccionDeUnicidadException si otro proceso insertó antes un dato que viola un índice único.
    Task<int> SaveChangesAsync(CancellationToken cancellationToken = default);

    Task BeginTransactionAsync(CancellationToken cancellationToken = default);
    Task CommitTransactionAsync(CancellationToken cancellationToken = default);
    Task RollbackTransactionAsync(CancellationToken cancellationToken = default);

    /// Descarta todos los cambios pendientes en memoria y deja de seguir las entidades cargadas.
    void DescartarCambios();
}

Por qué existe, si EF Core ya es un Unit of Work

Es una pregunta legítima: DbContext ya rastrea cambios y los guarda en una transacción. La respuesta está en la regla de dependencia: Aplicación no puede conocer a Entity Framework. Necesita un contrato propio (IUnitOfWork) para pedir «guardá», y la infraestructura lo implementa con el DbContext. Además, la implementación agrega cosas que el contexto no hace solo:

src/Retail.Infrastructure/Persistence/Repositories/UnitOfWork.cs (recortado)

public async Task<int> SaveChangesAsync(CancellationToken cancellationToken = default)
{
    try
    {
        return await _context.SaveChangesAsync(cancellationToken);
    }
    catch (DbUpdateConcurrencyException ex)
    {
        DescartarCambios();
        throw new ConflictoDeConcurrenciaException("Otro usuario modificó los mismos datos ...", ex);
    }
    catch (DbUpdateException ex) when (EsViolacionDeUnicidad(ex))
    {
        DescartarCambios();
        throw new RestriccionDeUnicidadException("El guardado chocó con otra operación ...", ex);
    }
    catch
    {
        // La base revirtió la transacción, pero el contexto vive mientras dura la pantalla:
        // sin limpiarlo, los cambios rechazados se guardarían con la próxima operación exitosa.
        DescartarCambios();
        throw;
    }
}

public void DescartarCambios() => _context.ChangeTracker.Clear();
  • Traduce errores técnicos a errores de Aplicación. Un DbUpdateConcurrencyException de EF se convierte en ConflictoDeConcurrenciaException: la pantalla lo entiende sin saber qué es EF Core.
  • Limpia el contexto cuando algo falla. Es la pieza que impide que un cambio rechazado «sobreviva» en memoria.

La clave: una sola instancia de DbContext

El repositorio y el Unit of Work no se hablan entre sí. Funcionan juntos porque ambos reciben, por inyección, la misma instancia de RetailDbContext (Scoped por pantalla). Ahí está la conexión entre las secciones 4 y 5:

Por eso _clienteRepository.AddAsync(cliente) y _unitOfWork.SaveChangesAsync() «se encuentran»: el primero anotó el cliente en el seguimiento del contexto; el segundo envía lo anotado. Si cada uno tuviera su propio contexto, SaveChangesAsync no vería nada para guardar.

Qué pasa dentro: el seguimiento de cambios

El DbContext lleva una libreta con el estado de cada entidad que cargó o agregó. SaveChanges recorre esa libreta y genera el SQL que corresponda a cada estado:

Las dos transiciones que más enseñan: Modified sucede sola, por el solo hecho de asignar una propiedad de una entidad cargada (por eso no hace falta UpdateAsync); y Detached es lo que provoca DescartarCambios: la entidad deja de estar vigilada y sus cambios pendientes se olvidan. Hay un cuarto estado, Deleted, para una entidad marcada para borrar: en Retail nunca llega a un DELETE, porque SaveChangesAsync la convierte en una baja lógica (Modified con DeletedAt completo).

Un guardado, varios agregados

El ejemplo más claro de por qué existe el Unit of Work es el registro de una compra que cierra un pedido. Cambia tres tipos de entidad: la compra, los artículos (stock y costo) y el pedido (pasa a «recibido»). Se guardan en un único SaveChangesAsync:

src/Retail.Application/Services/CompraService.cs (recortado)

// Se valida y se modifica el pedido en memoria (nada se guarda todavía)
var pedido = await _pedidoRepository.GetByIdAsync(dto.IdPedidoOrigen.Value, cancellationToken)
    ?? throw new DomainException("El pedido ... no existe o fue dado de baja.");

pedido.MarcarRecibido();                              // lanza si no está Emitido
await _pedidoRepository.UpdateAsync(pedido, cancellationToken);

// ... por cada renglón: compra.AgregarDetalle(...), articulo.IncrementarStock(...) ...

// Persistencia atómica ACID en un único SaveChanges
await _compraRepository.AddAsync(compra, cancellationToken);
await _unitOfWork.SaveChangesAsync(cancellationToken);

Mientras no se llama a SaveChangesAsync, nada de esto existe en la base: el pedido, la compra y los artículos son cambios en el seguimiento del contexto. En el instante del guardado, SQL Server los confirma o los revierte juntos. Una compra registrada con su pedido todavía abierto es un estado que no puede ocurrir (A-10).

Cuando un solo guardado no alcanza: la transacción explícita

Casi todos los casos de uso hacen un SaveChangesAsync. A veces hacen falta dos, y entonces la atomicidad se logra con una transacción explícita. El ejemplo real: registrar un término de clasificación junto con una categoría nueva. El término guarda el id de la categoría, y ese id no existe hasta que la categoría se guarda por primera vez.

src/Retail.Application/Services/TerminoClasificacionService.cs (recortado)

// T-1: el término guarda el Id de su categoría y la categoría nueva recién lo tiene
// después de guardarse. Son dos guardados, así que la atomicidad la da una transacción
// explícita: si el término falla, la categoría tampoco queda.
await _unitOfWork.BeginTransactionAsync(cancellationToken);
try
{
    var (categoria, rubro) = await AltaCategoria.PrepararAsync(_categorias, _rubros, dto.NombreCategoria, dto.IdRubro, cancellationToken);
    await PersistenciaDiccionarios.GuardarAsync(_unitOfWork, "...", cancellationToken);   // 1er guardado: la categoría

    string termino = await RegistrarEnMemoriaAsync(dto.Termino, categoria.Id, cancellationToken);
    await PersistenciaDiccionarios.GuardarAsync(_unitOfWork, "...", cancellationToken);   // 2do guardado: el término
    await _unitOfWork.CommitTransactionAsync(cancellationToken);                           // recién acá se confirma todo
    // ...
}
catch
{
    // ... se revierte la transacción ...
}

Es la excepción, no la regla. Si podés resolver el caso con un solo SaveChangesAsync, hacelo así: es más simple y ya es atómico.

Qué puede salir mal al guardar

El Unit of Work traduce tres situaciones, y cada una significa algo distinto:

SituaciónExcepción de AplicaciónQué la disparaEjemplo
Otro usuario modificó la misma fila mientras vos la tenías cargadaConflictoDeConcurrenciaExceptionUna columna row_version: SQL Server la cambia en cada UPDATE y EF Core la agrega al WHEREDos terminales emiten el mismo pedido. Articulo y Pedido tienen row_version; Cliente no
Otro proceso insertó un dato que viola un índice único un instante antesRestriccionDeUnicidadExceptionUn índice único (códigos 2601 o 2627 de SQL Server)Dos terminales dan de alta el mismo documento de cliente a la vez
Cualquier otra fallaLa excepción originalUna caída de la base, una restricción CHECK, etc.—

En los tres casos el Unit of Work descarta los cambios pendientes antes de relanzar, así que el llamador no tiene que hacerlo. Y la comprobación previa del servicio (FindAsync por documento) y el índice único no son redundantes: la primera da un mensaje claro en el caso común; el segundo cubre la carrera entre dos terminales, que la primera no puede ver.

DescartarCambios: por qué hace falta

Un DbContext de Retail vive lo que dura la pantalla, no lo que dura una operación. Eso es cómodo (las entidades cargadas siguen disponibles) pero tiene un riesgo: un cambio que se modificó en memoria y nunca se guardó sigue rastreado y se guardaría con la próxima operación exitosa de esa misma pantalla.

Por eso hay dos reglas de oro:

  • Si tu caso de uso modifica una entidad y después falla antes de guardar, llamá a DescartarCambios() antes de relanzar. ClienteService.ActualizarClienteAsync lo hace en su catch.
  • Si el guardado falla, no hace falta: UnitOfWork.SaveChangesAsync ya descartó.

Además, tras un guardado exitoso se libera el seguimiento, para que la próxima lectura traiga datos frescos y no choque con un conflicto falso (por ejemplo, CompraService lo hace tras guardar).

Qué tenés que llevarte
  • El repositorio anota y el Unit of Work confirma. Se encuentran porque comparten la misma instancia de DbContext (Scoped por pantalla).
  • Un SaveChangesAsync es una transacción: todo lo anotado (de uno o de varios repositorios) se guarda junto o no se guarda nada. Usá la transacción explícita solo cuando necesitás dos guardados.
  • Un conflicto de concurrencia y una violación de unicidad llegan como excepciones de Aplicación, ya con el contexto limpio. Si fallás vos antes de guardar, limpiá con DescartarCambios().
Autoevaluación 5: si el repositorio y el Unit of Work recibieran cada uno su propio DbContext, ¿qué pasaría?

El repositorio anotaría el cliente en el seguimiento de su contexto, y el Unit of Work llamaría a SaveChanges sobre otro contexto que no sabe nada de ese cliente: guardaría cero filas y no daría error. Es una falla silenciosa. Por eso el DbContext es Scoped (uno por pantalla, compartido por todas las piezas de esa pantalla) y por eso ValidateScopes está activado: para que el contenedor impida resolverlo con un ciclo de vida equivocado.

Defensa · Preguntas probables

Preparación para la defensa
Pregunta probable: ¿por qué ClienteService recibe interfaces y no crea el repositorio con new?

Por el principio de inversión de dependencias (la «D» de SOLID): las clases de alto nivel no deben depender de detalles de bajo nivel. Si ClienteService creara un Repository<Cliente>, quedaría atado a Entity Framework y a una base real, y no se podría probar en aislamiento. Con la interfaz en el constructor, el contenedor entrega la implementación real y una prueba entrega un doble. Además, la interfaz vive en Aplicación y la implementación en Infraestructura: es lo que hace cumplir la regla de dependencia.

Pregunta probable: ¿por qué se valida en el validador y también en el dominio? ¿No es duplicar?

Cumplen funciones distintas. El validador está en la frontera y da mensajes por campo, todos juntos, para que el usuario corrija de una vez. El dominio es la última barrera: garantiza que ninguna entidad inválida exista aunque otro código lo llame sin pasar por el validador. No se duplican las reglas: el validador reutiliza las del dominio (por ejemplo, Cliente.EsNombreValido). Lo único que se repite a propósito son las restricciones críticas en la base de datos (CHECK, índices únicos), porque son la defensa contra dos terminales actuando a la vez.

Pregunta probable: ¿por qué hay un repositorio y, además, un servicio de consulta?

Porque escribir y leer tienen necesidades opuestas. Para escribir se carga una entidad completa con seguimiento, se la modifica a través de su dominio y se guarda. Para mostrar un listado basta con una proyección a DTO, filtrada, ordenada y paginada dentro de SQL Server, sin seguimiento. Usar el repositorio para listar obligaría a traer entidades completas a memoria (RNF-03) y a filtrar fuera del motor (Ley 8). Es una versión liviana de CQRS: una vía para el comando y otra para la consulta.

Pregunta probable: ¿por qué solo las raíces de agregado tienen repositorio?

Porque una raíz es la única puerta de entrada a su grupo de entidades, y es la que protege sus invariantes. Si DetalleVenta tuviera su propio repositorio, alguien podría modificar un renglón sin pasar por Venta y romper la regla de que el total coincida con los pagos. El tipo genérico IRepository<T> where T : BaseEntity, IAggregateRoot hace que ese error ni compile.

Pregunta probable: ¿por qué el DbContext es Scoped, y por qué un alcance por pantalla?

Scoped hace que todas las piezas de una operación compartan un contexto, que es lo que permite que el repositorio y el Unit of Work se encuentren. Un alcance por pantalla hace que dos pantallas nunca compartan entidades rastreadas (lo que una modifique sin guardar no contamina a la otra) y que al salir de una se libere su contexto y la memoria que usaba (RNF-03). Si fuera Singleton viviría para siempre y acumularía entidades; si fuera Transient, cada pieza tendría el suyo y el Unit of Work no vería lo que anotó el repositorio.

Pregunta probable: si EF Core ya es un Unit of Work, ¿para qué tienen IUnitOfWork?

Porque Aplicación no puede depender de Entity Framework (Ley 1) y necesita un contrato propio para pedir «guardá». Además, la implementación agrega comportamiento: traduce los errores de EF a excepciones de Aplicación (ConflictoDeConcurrenciaException, RestriccionDeUnicidadException) y limpia el contexto cuando el guardado falla, para que un cambio rechazado no se guarde con la próxima operación.

Pregunta probable: dos terminales dan de alta el mismo cliente a la vez. ¿Qué pasa?

Ambas pasan la comprobación previa (FindAsync no encuentra nada) porque todavía no hay nadie guardado. La primera guarda y la segunda choca con el índice único del documento (filtrado por deleted_at IS NULL). SQL Server rechaza la inserción, el Unit of Work lo traduce a RestriccionDeUnicidadException, descarta los cambios pendientes y el formulario muestra el error sin perder lo escrito. La comprobación previa da el mensaje amable en el caso común; el índice es la garantía real.

Pregunta probable: ¿por qué el borrado es lógico, y cómo no choca con el índice único del documento?

En un sistema comercial no se pierde el historial: las ventas y cobranzas de un cliente deben seguir existiendo aunque el cliente se dé de baja (Ley 3). Se marca DeletedAt y un filtro global oculta esa fila en todas las consultas. El índice único del documento se declara solo para las filas vigentes (WHERE deleted_at IS NULL), así que un cliente dado de baja libera su documento y se puede volver a registrar.

Pregunta probable: ¿por qué ClienteService llama a DescartarCambios en un caso y no en otro?

Si el guardado falla, el Unit of Work ya descarta. Pero si el dominio rechaza una operación después de que otra parte del caso de uso ya modificó la entidad (por ejemplo, ActualizarDatos cambió el nombre y luego se rechaza el límite de crédito), el guardado nunca se intenta y nada limpia el seguimiento. Como el contexto vive lo que la pantalla, ese cambio «a medio hacer» se guardaría con la próxima operación exitosa. Por eso el servicio descarta explícitamente en su catch, y hay una prueba que lo exige.

Pregunta probable: ¿qué pasa si un Singleton recibe un servicio Scoped?

El servicio Scoped queda capturado para siempre (captive dependency): un DbContext viviría más que su pantalla y compartiría estado entre pantallas. El proyecto lo previene con ValidateScopes y ValidateOnBuild, que hacen fallar el arranque, y con una prueba que construye el proveedor con la configuración real. Cuando un Singleton necesita algo Scoped, no lo recibe: recibe IServiceScopeFactory y crea un alcance cuando lo necesita.

Pregunta probable: ¿por qué el ViewModel no usa directamente el DbContext?

Porque rompería la regla de dependencia (Ley 1): la pantalla pasaría a conocer el esquema y a saltearse las validaciones y reglas del dominio. Y haría imposible probar el ViewModel sin una base. Con el servicio por interfaz, la prueba del ViewModel reemplaza al servicio y verifica solo lo suyo: que cargue la lista, que cambie el estado de «ocupado» y que habilite o deshabilite los botones.

Resumen de lo aprendido
  • Una pieza, una responsabilidad: entidad (reglas), DTO (datos), validador (entrada), servicio (orden), repositorio (cargar y anotar), consulta (leer en SQL), configuración (esquema), ViewModel (estado), vista (enlace), diálogo (ventanas).
  • Las dependencias apuntan hacia adentro y se entregan por interfaces. Esa es la regla que sostiene todo lo demás.
  • El contenedor construye el grafo. El ciclo de vida decide quién comparte qué: Scoped por pantalla hace que el repositorio y el Unit of Work compartan un contexto.
  • El repositorio anota, el Unit of Work confirma. Un SaveChangesAsync es una transacción: todo o nada. Los errores de guardado llegan traducidos y con el contexto limpio.
  • Escribir y leer van por caminos distintos: entidad y repositorio para escribir; DTO y consulta en SQL para mostrar.
  • Nunca se borra: se marca. Un filtro global y un índice filtrado hacen que la baja lógica sea invisible y no estorbe.
